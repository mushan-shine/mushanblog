> [!abstract]
> 上一期我们看到：从插上电，到服务器的第一个用户态程序（systemd）被拉起来。可这只是开机。真正的问题是——**一堆硬件要跑一堆程序、对外提供一系列服务，谁来把这堆硬件组织成好用、有序、安全的整体？** 答案就是操作系统。
>
> 本期我们换一个视角：不背概念，而是把操作系统当成一个「硬件大管家」，看它同时扮演的**四个角色**——资源调度者、硬件抽象者、安全守护者、内核接口提供者。再用「磁盘上一份代码怎么跑起来」这一个例子，把这四个角色的具体表现一次性串起来。

**为什么需要操作系统：** 从「一堆硬件要跑一堆程序」这个任务出发，会自然逼出四种需求——服务器资源有限要争夺，于是需要**资源调度者**；硬件太难用要抽象，于是需要**硬件抽象者**；共享资源会互相伤害要守护，于是需要**安全守护者**；程序被限权却又想办事，于是需要**内核接口提供者**。操作系统的本质，就是把硬件组织成好用、有序、安全的整体。

## 先厘清：程序、进程、线程

拆解四个角色之前，先分清三个词，后面全靠它。

**程序**是躺在磁盘上的一个文件、一堆静止的代码，不占内存、不占 CPU。**进程**是程序被加载进内存后的运行实例：有自己专属的、独立的虚拟内存空间（代码段、数据段、堆、栈），有运行现场（执行到哪、寄存器值），有运行状态。**线程**则是进程里那条真正在跑的执行流。

一个好记的比方：程序是**菜谱**，进程是**照着菜谱正在做的这顿饭**，而线程就是**正在颠勺的那只手**。

## 一个例子：磁盘上的代码，如何跑起来

整期最关键的一张图。我们只问一件事：磁盘里有一份代码，怎么把它运行起来？跟着这条链路，四个角色会依次登场。

<figure style="margin:1.8em 0;text-align:center"><img src="/tech/server-operating-system/program-to-run.svg" alt="一份磁盘上的代码如何跑起来" style="width:100%;display:block"></figure>

**第一步，这份代码怎么被读起来？（硬件抽象者登场）** 代码存在磁盘上，但磁盘本身不懂「文件」这个概念，它只有块号这些底层逻辑。是操作系统在裸盘上盖了一层**文件系统**，把一堆编号的裸块组织成文件和目录，并维护「文件名 → 磁盘块号」的映射，我们才能以文件的形式去读它。至于「谁去触发读取」——如果是在 shell 里运行，就由 shell 发起；但用户态进程没权限直接读磁盘，最终都要**通过系统调用、由内核去读**（这里内核接口提供者也搭了把手）。

**第二步，进程怎么被拉起来？（安全守护者登场）** 要有独占的内存、要生成对应的控制块。操作系统给每个进程造一套**独占内存**：每个进程有自己的页表，虚拟地址经 CPU 的 MMU 硬件翻译成物理地址，别人的地址在它的页表里根本不存在，越界还会被硬件当场拦截。除了把代码数据读进这块虚拟内存，内核还要建**进程控制块（PCB）**和**第一个线程控制块（TCB）**：PCB 分配唯一的进程 ID、记录内存信息（那张进程专属页表）、登记已打开的资源；TCB 初始化运行现场（把程序计数器设为代码入口地址）、记录优先级和初始状态。

> 记法：PCB 记录的是「这个进程有什么资源」（内存、打开的文件等进程内线程共享的资源）；TCB 记录的是「这条执行流跑到哪、怎么跑」（运行现场、状态、栈等线程私有资源）。

**第三步，线程就绪了就能跑吗？（资源调度者登场）** 还不能。此刻只是除 CPU 以外的资源都备好了，线程处于**就绪态**，内核为它选一个合适的核心、挂到该核心的就绪队列里排队。最后要等到有 CPU 核心真正**调度**到它——调度器从就绪队列把它挑中，内核把线程的运行现场恢复到 CPU、让 MMU 换用它的页表、CPU 从代码入口开始取指执行——它才由就绪态转为**运行态**，真正跑起来。

至此，操作系统作为资源调度者、硬件抽象者、安全守护者、内核接口提供者这四个角色的具体表现，已经在这一个例子里全部露过脸。下面逐个展开。

## 角色一 · 资源调度者

核心思想是：资源有限、竞争者众多，调度者的核心工作就是**在竞争中做仲裁，在效率和公平中权衡**。它主要调度三大类资源。

**① CPU —— 进程/线程调度。** 问题是 CPU 核心数远小于就绪线程数，得决定谁来跑、跑多久。手段是调度器 + 调度算法，目标在吞吐量、响应时间、周转时间、公平性之间权衡。关键机制是**时间片轮转 + 上下文切换**：每个 CPU 核心有自己的就绪队列，只对自己队列上的线程轮转；一次上下文切换要保存/恢复寄存器、程序计数器、栈指针等现场。常见算法有先来先服务（FCFS）、短作业优先（SJF）、优先级调度、多级反馈队列（MLFQ）等。

**② 内存 —— 物理内存分配与虚拟内存。** 问题是物理内存有限、多个进程都要用，还不能互相踩到对方的数据。手段有三：**物理内存分配**（管哪些页被占用、哪些空闲，物理内存被切成固定大小的块叫页框，通常 4KB，用位图或空闲链表追踪，用伙伴系统分配连续物理页、slab 分配器再做细粒度切分）；**虚拟内存**（给每个进程一个独立、连续的虚拟地址空间，由 MMU + 页表在运行时把虚拟地址翻译成物理地址，实现地址空间隔离）；**换页/交换**（物理内存不够时，把不常用的页换到磁盘）。

这里的翻译过程值得单独看一眼：

<figure style="margin:1.8em 0;text-align:center"><img src="/tech/server-operating-system/address-translation.svg" alt="虚拟地址到物理地址的翻译" style="width:100%;display:block"></figure>

虚拟地址被切成「页号 VPN + 页内偏移」，查页表得到「帧号 PFN」，再和不变的偏移拼接成物理地址。64 位地址空间若用单级页表会大得离谱，所以用**多级页表**——只为实际用到的部分建表，省内存；但多级页表一次翻译要访存好几次，很慢，于是用 **TLB（快表）** 缓存最近用过的「页号 → 帧号」映射。进程启动时不会把所有页都装进内存，而是用到哪页装哪页；页不在内存时硬件触发**缺页中断**陷入内核，若没有空闲帧就得按**页面置换算法**选一页换到磁盘交换区——常见的有 FIFO（最早进的先换）、LRU（最近最少使用）、OPT（理论最优，换未来最久不用的）、以及实际系统常用的 **clock（时钟/二次机会）**（看每页的访问位，遇 1 清 0、遇 0 换出）。

**③ I/O 与外设 —— 带宽与访问的分配、排队。** 问题是磁盘、网卡等设备速度慢，且被多个进程争用。手段有 I/O 调度（为对应设备维护请求队列）、缓冲（buffer）、缓存（cache）、DMA 等。目标是既要整体吞吐高，又要避免某个进程被饿死。

## 角色二 · 硬件抽象者

硬件五花八门：不同厂商的磁盘、网卡、显卡、寄存器、指令集、通信协议各不相同。如果每个应用都直接面对具体硬件，那将极难移植、极难维护。

操作系统的解法是**用统一的抽象把硬件差异藏起来**，让上层程序面对「文件」「Socket」这种一致、简单、稳定的概念，而不用管底下具体是哪块硬件。抽象要落地，最贴硬件那一侧靠的是**驱动程序**——驱动把具体硬件的操作翻译成内核内部统一的接口。正因如此，换一个新硬件往往只需装一个驱动，上层软件不用改。直白说，操作系统在上层应用与硬件之间起**抽象层**作用，把复杂的底层硬件包装好，让上层用得省心。

## 角色三 · 安全守护者

一台机器上同时跑着多个互不信任的程序，安全守护者要保证：一个程序的错误或恶意行为，不会破坏其它程序、也不会破坏内核本身。它主要拆成两个能力。

**地址空间隔离**：每个进程有独立的虚拟地址空间，进程 A 无法访问进程 B 的内存（别人的地址在它页表里根本不存在，越界被硬件拦截）。**特权隔离**（内核态/用户态）：用户程序无法直接执行特权指令、无法直接碰内核的数据结构。合起来，就是既让进程能合法共享资源（文件、设备等），又能判断谁有资格用、比如谁能读哪个文件。

## 角色四 · 内核接口提供者

先讲清**内核态与用户态**：它们其实是 CPU 的两种运行模式、两种权限级别（x86 上对应 Ring 0 最高权限与 Ring 3）。设想如果不区分、CPU 只有一种特权：所有代码都能执行任意指令、访问任意内存、直接操作任意硬件，那整个系统会非常脆弱——随便一个数组越界 bug 都可能让整台机器崩溃。所以，把「能造成全局破坏的能力」（直接操作硬件、修改页表、切换地址空间等特权指令）关起来锁进内核态；普通、不影响全局资源的指令留在用户态。

于是普通程序运行在用户态，当要操作硬件资源却没权限时，就需要**通过系统调用陷入内核态**去执行。

<figure style="margin:1.8em 0;text-align:center"><img src="/tech/server-operating-system/user-kernel-mode.svg" alt="用户态内核态与系统调用" style="width:100%;display:block"></figure>

一次系统调用的过程是：硬件把 CPU 切到内核态、跳到内核预先设定好的固定入口；内核在入口处按系统调用号查表，找到对应的处理函数，校验参数与权限后执行，办完再返回用户态。这道「受控的门」，就是内核接口提供者的价值——既让用户程序能办需要特权的事，又不把特权直接交到它手里。

## 结语 · 承上启下

这一期我们把操作系统拆成了四个角色，并用「一份代码如何跑起来」把它们串成了一条完整链路。回头看，操作系统做的所有事，都指向同一个目标：**把一堆杂乱、危险、难用的硬件，组织成一个好用、有序、安全的整体，让上层程序省心地运行。**

**下一站 · 平台层：** 单机上把服务跑顺已经能理顺了。但当成百上千个应用、数十上百台服务器出现时，新的痛点又会冒出来——怎么把一台台孤立的服务器抽象成一个大资源池？于是虚拟机、容器、Kubernetes、云平台会像这一期的四个角色一样，被一步步逼着诞生。
