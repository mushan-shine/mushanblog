> [!abstract]
> 上一期我们把「单机」讲透了：操作系统怎么调度硬件、程序怎么跑起来。但现实里很少有服务只跑在一台机器上——**一旦应用变多、机器变多，怎么把一台台孤立的服务器捏成一个统一的大资源池，还能自动管理、维护？** 这就是本期的主角：平台层。
>
> 本期不按知识点罗列，而是讲一个成长故事：跟着一个不断长大的服务，看它如何一次次撞墙、又如何被逼出下一代技术。这条线依次经过四个关卡——**虚拟机 → 容器 → Kubernetes → 云平台**。

**平台层的定位：** 它站在操作系统之上、业务代码之下，把「业务活下去必须、却不属于任何具体业务」的**通用能力**抽出来，让上层只管写业务。**云平台的本质 = 数据中心级的操作系统。**

![演进主线](/tech/server-platform-layer/evolution.svg)

## 关卡 00 · 一台物理机，不够用了

故事从一台物理机开始。你买了台服务器，跑上第一个应用，一切安好。可很快，第二个、第三个应用也要上线。你把它们塞进同一台机器——麻烦来了：A 应用要 Python 3.8，B 应用偏要 3.11；两个应用抢同一个端口；一个崩了顺手把整台机器拖垮。更扎心的是，这台机器的 CPU 常年只用了 15%，**大量资源白白浪费**，可你又不敢多塞应用。

于是有了第一个念头：**能不能把一台物理机，切成好几台互不干扰的「小机器」？**

## 关卡 01 · 虚拟机：把「硬件」虚拟化

虚拟机的做法，是在硬件和操作系统之间插一层 **Hypervisor**，由它把物理硬件切开、隔离，再分给一台台虚拟机；每台虚拟机里都装着自己完整的操作系统（Guest OS）和应用，谁也看不见谁。按 Hypervisor 有没有「宿主操作系统」，分两型：**Type-1（裸金属型）** 没有 Host OS，直接趴在硬件上，数据中心用它；**Type-2（宿主式）** 跑在宿主系统里（比如你电脑上的 VMware），方便但多一层损耗。

![虚拟机与容器分层对比](/tech/server-platform-layer/vm-container.svg)

难点在于：Guest OS 一直以为自己独占着真实硬件，可它并没有。Hypervisor 要在它「不知情」的情况下把这个幻觉圆下去，于是有了三处关键虚拟化。

**① CPU 虚拟化——「谁有资格执行特权指令」。** Guest OS 想执行特权指令，但它没资格。早期只能靠软件翻译，很慢。后来 Intel 出了 **VT-x**、AMD 出了 **AMD-V**，在硬件层加了一个新维度：把 CPU 分成 **root 模式**（给 Hypervisor）和 **non-root 模式**（给 VM）。VM 一执行敏感指令，就自动**陷入（VM Exit）**，交给 Hypervisor 代劳。结果每个 Guest OS 都心安理得地以为自己在管着 CPU。

**② 内存虚拟化——「你以为的连续内存是假的」。** Guest OS 以为自己管着一块从 0 开始、连续的物理内存，其实那是 Hypervisor 编的。真实寻址要走**两级翻译**：`Guest 虚拟地址 → Guest 物理地址 → 真实物理地址`。早期靠影子页表由软件维护，后来硬件直接支持，性能大增。

**③ I/O 虚拟化——「网卡磁盘怎么共享」。** 三种方式，性能一路递增：**全虚拟化**（软件模拟一张假网卡，慢）→ **半虚拟化 virtio**（Guest 换上高效专用驱动，它「知道」自己在虚拟机里，中）→ **硬件直通 SR-IOV**（把真实设备直接分给 VM，最快）。

## 关卡 02 · 容器：虚拟机太重了

问题出在：**每台虚拟机都背着一整个操作系统。** 你只是想跑一个几十兆的小服务，却要为它配一台带完整 OS 的虚拟机——几个 G 起步，开机还要等系统慢慢启动。这时有人想通了：我要隔离的其实是「应用」，并不需要为每个应用都复制一份内核。同一台机器上的应用，完全可以**共享同一个内核**，只要让它们「看不见彼此」就行。

**容器的实现本质：** = **namespace**（管你能看见什么）+ **cgroup**（管你能用多少）。

**① namespace（命名空间）——管「你能看见什么」。** 内核把各种资源视图切成一份份独立的：**PID namespace** 让容器里的进程以为自己进程号从 1 开始；**network namespace** 给它独立的网卡和 IP；**mount namespace** 给它独立的文件系统视图……于是容器里的进程，活得就像独占了一台机器。

**② cgroup（控制组）——管「你能用多少」。** 限制每个容器最多用多少 CPU、内存、I/O 带宽，超了就限流或直接 kill。

**③ 联合文件系统（overlayFS）——管「镜像怎么分层」。** 容器镜像是一层层叠起来的：**基础系统层 + 依赖层 + 你的应用层**。多个容器可以共享底下相同的层，既省空间又快。

## 关卡 03 · Kubernetes：几百个容器谁来管？

当你的服务真正火了，一台机器扛不住，你有了几十上百台机器。新容器该放哪台？某台宕了容器谁在别处拉起？流量高峰怎么自动多开副本、低谷怎么缩回省钱？靠人盯根本盯不过来。**由此，集群调度系统 Kubernetes（k8s）诞生了。**

理解 k8s，先记住几个核心角色：**Pod** 是调度的最小单位，装一个或几个紧密相关、共享网络与存储的容器（注意 k8s 不直接调度容器，调度的是 Pod）；**Node** 是一台工作机器；**控制平面**是大脑，含 API Server（唯一入口）、Scheduler（选节点）、Controller Manager（调和纠偏）、etcd（状态库）；**kubelet** 是每个 Node 上的代理，负责真正把 Pod 拉起来并汇报状态。

![Kubernetes 架构](/tech/server-platform-layer/k8s.svg)

整合成一句话，k8s 是一个**声明式的调和系统**：你不告诉它「怎么做」，只告诉它「我想要什么」（比如这个服务要 3 个副本）。期望状态存进 etcd 后，Scheduler 和 Controller Manager 不停监控、不断纠偏（挂一个补一个），kubelet 在节点上落地执行。

**容器到底是谁拉起来的？** 是**容器运行时**，分两层：**高层运行时**（containerd、CRI-O）管镜像和生命周期；**低层运行时**（runc、crun、youki）负责创建真正的容器进程——创建 namespace、创建 cgroup、启动进程（还记得关卡 02 那两个本质吗？绕了一圈又回来了）。

**CRI——解耦 kubelet 与运行时。** 高层运行时各家不同，k8s 不为每种写对接代码，而是抽出一套 gRPC 接口 CRI：kubelet 是客户端，运行时是服务端。对 kubelet 来说，跟 containerd 说的 CRI 和跟 CRI-O 说的 CRI 毫无区别，差异都藏在各自内部。**同一份接口，两套内部实现。**

**一通百通：** 同样的「插座」思路也用在存储和网络上：存储有 **CSI**，网络有 **CNI**。看懂了 CRI，CSI/CNI 一通百通——都是「同一份标准接口 + 各厂自己实现」。

## 关卡 04 · 干脆租一整个数据中心——云平台

你能自建这套东西了，但维护它本身就是一份全职工作——机房、电力、网络、硬件更换……于是最后一个念头冒出来：能不能不自建，直接「租」一份现成的、弹性的、免运维的资源？**云平台**就是答案。它把上面这套复杂技术打包好、运维好，按需租给你，账单按用量走。

![云平台三层](/tech/server-platform-layer/cloud.svg)

它的本质，是从单台服务器到多台构成的资源池，**不断向上抽象**，把复杂基础设施封装成不同层次的服务。通常分三层：**IaaS** 租「资源」（虚拟机、云硬盘、虚拟网络）；**PaaS** 租「运行平台」（容器平台、数据库、中间件、DevOps）；**SaaS** 租「现成软件」。

但云平台远不止「资源抽象」。要让成千上万个互不信任的用户在同一批物理机上安全共享资源，还得再叠两层能力：

| 资源管理层（让大量用户安全共享资源） | 自动化运营层 |
|--------------------------------|-------------|
| 多租户、身份认证、权限控制 | 编排调度、自动化扩缩容 |
| 配额管理、资源隔离、服务目录 | CI/CD、运维自动化、可观测性 |

## 结语 · 这条故事线的意义

回头看，从物理机到云平台，每一步都不是凭空发明，而是**被上一步的痛点逼出来的**：硬件浪费逼出虚拟机，虚拟机太重逼出容器，容器太多逼出 k8s，自建太累逼出云平台。抓住这条「痛点→方案」的链子，你就不会把这些名词当成孤立的知识点去背，而是能顺着因果推出来。

**下一站 · 模型层：** 同一条故事线还会再演一遍：当「单机装不下、也跑不动一个大模型」成为新的痛点时，分布式训练、推理服务化、模型编排……又会像当年的虚拟机和 k8s 一样，被一步步逼着诞生。
